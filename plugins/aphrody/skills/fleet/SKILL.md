---
name: fleet
description: "Run a command, schedule builds, deploy or check on the fleet (equal nodes n1 and n2, load placed live), gcloud Cloud Build. Use for any remote ssh/scp/systemctl/build; never a heavy build on the PC CPU."
---

1. Always check live capacity and peer locks first: run `bun configs/claude/scripts/fleet-inventory.ts` (every node of `cluster/build.toml`) and `bun configs/claude/scripts/build-cluster.ts measure` (or `ssh <host> uptime`) and list live peer sessions with the `claude_sessions` MCP tool (`bun ~/.claude/scripts/notify.ts --list`) before writing under the shared build dir (`<work>` of the host) or launching heavy Cargo/C++ builds; `bun configs/claude/scripts/build-cluster.ts place [--mem G] [--disk G]` names the node with the most free cores that has the memory and disk, `run [--mem G] -- <cmd>` places and runs.
2. Launch every long remote command (builds, installs, syncs, benchmarks, kernel compiles) directly inside a detached `tmux` session (`ssh <host> "tmux new-session -d -s <job> '<cmd>'"`; inside a repository checkout `bun tools/fr1.ts run -- <cmd>` syncs by git and runs it) and inspect non-blockingly with `ssh <host> "tmux has-session -t <job>; tmux capture-pane -p -t <job> | tail -20"`. Announce a heavy build to the live sessions with `claude_inject` (or `bun ~/.claude/scripts/notify.ts --to all "<message>"`). For short one-liners, pipe single-quoted heredocs through `@' ... '@ | ssh <host> "tr -d '\r' | bash"`.
3. Exit 255 / slow host: `@' ... '@ | ssh <node> "tr -d '\r' | bash"` checking `uptime` (and clearing stale processes only when owned by your task/session).
4. Deploy a file: `scp -q <src> <host>:<work>/X/` after ensuring `<work>/X` ownership via heredoc (`<work>` from `assets/os/fleet_cluster.toml` or `ay.toml`).
5. Service: `ssh <node> "sudo systemctl restart <svc> && systemctl is-active <svc>"`.
6. Prove a deploy with content, not a status: rendered page or real API response payload check; bare HTTP 200 proves nothing.
7. Never break a service: verify on one node, then the other; a service runs on both nodes behind Cloudflare load balancing or a tunnel with failover. Nodes are equal, no node is named for a role.
8. Compute targets: the cluster nodes of `cluster/build.toml` (`n1` 12c/45G Haswell x86-64-v3, `n2` 8c EPYC 9354P Zen 4 x86-64-v4/32G; secondary aliases `fr1` and `prd` until every reference is migrated), equal roles: builds, CI runners, agents, services; one resource policy on both (`[policy]`: build bursts run in `fw-build.slice`, CPUWeight 50, MemoryHigh 40% and MemoryMax 55% of the node's RAM, `Nice=19`, idle IO); gcloud Cloud Build (`gcloud builds submit`) and Cloudflare Containers as burst when every node is saturated (`place` fails with that hint); Cloudflare Workers and R2 for edge compute and artifacts; the local RTX 4070 for GPU work (CUDA, wgpu, model inference). Build with `RUSTC_WRAPPER=sccache`, `CARGO_INCREMENTAL=0` and the linker of item 14 (rustc's default rust-lld).
9. Canonical build layout on every node (`<work>` is `/srv/xbuild` on n1, `/srv/build` on n2; the n1 layout is the reference) (`ay.toml [paths.build].work` = `/srv/xbuild`, XFS on LVM `xbuild` over sdb+sdc, 805G; the root sda is ext4 and must stay under 70%): one checkout per repo at `$WORK/src/<repo>` (`~/src` is a symlink to it), shared `CARGO_TARGET_DIR=$WORK/target/<repo>` chosen by the cargo shim `$WORK/bin/shims/cargo` (first in PATH, from the git toplevel name; an explicit `CARGO_TARGET_DIR` wins), `SCCACHE_DIR=$WORK/cache/sccache`, `TMPDIR=$WORK/tmp` (set in `/etc/environment` and `/etc/profile.d/aphrody-work.sh`). Agents work in place on main with disjoint paths; no per-agent clones, no `~/ci`, `~/build`, `~/wb`. Benchmarks use a `git clone --shared` under `$WORK/bench`, removed after.
10. Build cluster as code: `cluster/build.toml` is the single source of node names (`<node_prefix><index>`), mesh addresses, ports, paths, policy and linker versions; `bun configs/claude/scripts/build-cluster.ts plan|apply|status` renders and installs the sccache-dist scheduler (pinned by `[scheduler].host`, moved by editing that line and applying) and a server on every node, restarting only units whose config changed; `ssh` adds the node names as aliases next to the old ones in the PC ssh config, `hostnames` sets system hostnames and the `<node>.mesh` DNS block, `linkers` builds mold and wild per node, `probe <node>` runs a cold 24-crate cargo build through sccache-dist, `failover` stops each unit in turn and proves the build still completes, `batch` runs the same job set pinned or placed. NativeLink: scheduler (`[nativelink].scheduler`) and a worker on every node (`/etc/nativelink/*.json5`). Shared Rust cache: R2 bucket `aphrody-sccache` through `<work>/sccache-r2.env`, mode 600, `SCCACHE_BUCKET`, `SCCACHE_ENDPOINT`, `SCCACHE_REGION=auto`.
11. The nodes differ in ISA: n2 is Zen 4 (x86-64-v4, AVX-512), n1 is Haswell (x86-64-v3, no AVX-512). Never copy a binary from one node to the other (`sccache-dist` from pacman crashes with SIGILL on n1); build it on the node with `RUSTFLAGS="-C target-cpu=<node target_cpu>"` (sccache-dist: `cargo install sccache --version 0.19.0 --locked --features "dist-client dist-server vendored-openssl"`; mold and wild: `build-cluster.ts linkers`). Shipped binaries target x86-64-v3 so they run on both.
12. n2 builds: user `builduser`, `RUSTUP_HOME=/srv/build/rustup CARGO_HOME=/srv/build/cargo`, checkout `/srv/build/src/<repo>` (git clone, never NFS: the NFS export is `<work>/shared` only), targets `/srv/build/target` on the btrfs subvolume `/srv/build` (zstd:1), long builds run through `systemd-run --slice=fw-build.slice -p Nice=19 -p IOSchedulingClass=idle`.
13. Measured limits of the cluster (2026-11-21, fw-bin release, thin LTO): sccache-dist distributes compiles to both servers (`sccache --dist-status` shows 2 servers, 20 CPUs) but `libc 0.2.191` fails in the sandbox (`bits/../../x86/...` path through an empty directory), so cargo builds of fw cannot use it until libc or sccache changes; R2-backed sccache hits across hosts only for crates whose absolute paths match (30 of 99 hits with `CARGO_HOME` and target dir under the same `/srv/cb` path on both nodes, 0 with different paths); workspace crates still differ because cargo resolves the checkout to its real path (`/srv/build` on n2, `/srv/xbuild` on n1).
14. Linkers, measured by `bun configs/claude/scripts/linker-bench.ts` (fw-bin release link replayed three times per linker, 2026-11-21): rust-lld (rustc 1.100's default on x86_64-linux-gnu) is the fastest on both nodes (median 0.558 s on n1, 0.278 s on n2), wild 0.595 s and 0.389 s, mold 3.0.0 1.217 s and 0.699 s, GNU ld 2.961 s and 0.91 s; mold and wild peak at 19 and 12 MiB of RSS against 65 and 66 for lld. `[linkers].default` of `cluster/build.toml` is therefore `lld`; mold and wild are built per node for its own ISA (`build-cluster.ts linkers`, `/usr/local/bin`) and stay available. `build-cluster.ts cargo-config` writes each node's cargo-home default (shipped `target-cpu=x86-64-v3`, never `native`, which poisons caches shared across ISAs).
