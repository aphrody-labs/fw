# fw-rag/codegraph

Native code graph (nodes, EXTRACTED and INFERRED edges with confidence, communities, god nodes, query, path and explain, report, graph.json) stored in the home database. Own implementation of the Graphify concepts (Apache-2.0, see NOTICE). Ships the `fw-graph` binary, which `fw graph` runs.

Legacy name: this unit was published on crates.io as `aphrody-code-graph`. It is restored here as `fw-rag/codegraph` (`publish = false`; nothing is published from this repository by hand).

| Rust crate | `crates/fw-rag` |

```sh
cargo test -p fw-rag --features codegraph
cargo clippy -p fw-rag --features codegraph --all-targets -- -D warnings
```

Rust builds run on the build host or in CI, not on a workstation.

## What goes into the graph

- **Files.** The walk honours `.gitignore` (with or without a `.git` directory), `.rgignore`, `.fdignore` and `.graphifyignore`, and the hard deny list of the store. The build report counts what the ignore files removed (`ignored`).
- **Generated code is left out**: a file is generated when a comment line in its first 24 lines carries a generator marker (`@generated`, `Generated by`, `Code generated`, `DO NOT EDIT`, `auto-generated`, ...; doc comments `//!` and `///` do not count) or when its path is a known generated place (`generated/`, `pb/gen/`, `*.pb.rs`, `*_pb.ts`, `*.min.js`, ...). `wrangler types` output is caught by its header. Only a record of the file is cached (`skipped`), nothing is parsed, and the report says how many files were left out. To keep them, set `FW_GRAPH_INCLUDE_GENERATED=1` (or call `pipeline::build_graph_with` with `BuildOptions { include_generated: true, .. }`): their nodes are then marked `generated` (also in `graph.json`) and are never hubs. The cache serves both modes.
- **External symbols** (a crate or package outside the corpus) are one node per item (`serde_json::Value`, `serde::Serialize`, `node:fs::readFileSync`), marked `external` (also in `graph.json`), with the crate or package as `package` and never a source file. They come from `use` declarations, type references, implemented traits and calls. They are not hubs, have no community and do not take part in community detection, so a type used everywhere cannot glue unrelated code together. The standard library is imported as external nodes too, but calls into it are only counted. Which names are external comes from the `Cargo.toml` dependency tables (without a manifest, any lower-case root that is not a module of the crate); JS built-ins and npm packages come from the specifier.
- **Never nodes**: `super`, `self`, `crate`, `Self`, generic parameters (`T`, `A`), associated type names (`Item` in `Stream<Item = T>`, `Out` in `<T as Tr>::Out`).
- **Type aliases** are definitions (`pub type Result<T> = ...`), so a reference resolves to them instead of a stub. A crate's `Result` is left out of the god nodes.

## Resolution

Rust paths are located in the module tree of the corpus (`extract/rpath.rs`): `crate::`, `self::`, `super::` (also inside `mod tests`), another crate of the corpus, a child module, a `use` alias, then looked up in the files of the module, through `pub use` re-exports and `pub use m::*`. The same resolver gives `use` declarations (`imports_from` edges to the definition, the module file or the external item), type references (a reference never folds onto an enum variant) and calls:

- `a::b::f()`, `Type::f()`, `Self::f()`, `x.f()` where `x` is `self`, a typed parameter, a `let` of an obvious type (`T { .. }`, `T::new()`, a function of the file with a declared return type, `.unwrap()` and `?` of those) or a field of a struct of the file (`self.db.query()`, through `Arc`, `Rc` and `Box`).
- A call whose path is placed in a module of the corpus but not defined there is unresolved, never guessed from a homonym of another module. A method of a type resolves to the impl beside the type when several types of a crate share a name.
- Calls through a local binding (parameter, `let`, closure) that nothing defines are counted as `local`; `Type::default()` and the like on a type the corpus does not define are derives or std traits and count as `external`.
- TypeScript: `tsconfig.json` (`baseUrl`, `paths`, relative `extends`) resolves non-relative specifiers (EXTRACTED); JS globals and parameters called as functions are not unresolved.

`AssembleStats` (printed in the `build` summary) breaks the calls down: `same_file`, `cross_file`, `external`, `local`, `unresolved` with `unresolved_by` (`path_unresolved`, `method_not_found`, `ambiguous`, `no_definition`, ...), and the `use` names (`uses_resolved`, `uses_external`, `uses_unresolved`).

## Report

`GRAPH_REPORT.md` keeps the lines `fw graph` consumers parse (`N nodes, M edges, K communities`, `## God nodes`, `## Communities`). God nodes are symbols, not files, not external, not generated: ranked by dependency edges (calls, references, imports, implements, inherits) of the node and of its members, with the number of files they come from. `## Packages` gives one line per crate or package: files, nodes, hubs, what it uses, what uses it and its main external dependencies; `## External dependencies` lists the outside packages the code leans on most.
