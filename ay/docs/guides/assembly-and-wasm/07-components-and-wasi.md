# 7. Components and WASI

Chapters 1 to 6 worked with core WebAssembly: a module with numbers in, numbers out and one linear memory. This chapter lifts the corelib of chapter 8 (freestanding C23, built with clang) from a core module to a component with typed interfaces, composes it with an app, a console and a driver, and runs the result on Wasmtime. Every command and output below was produced in this session (2026-11-16, the clock passed UTC midnight during the work); the tool versions are named where they matter.

## 7.1 Core module versus component

A core module (chapters 5 and 6) has imports and exports of four value types (`i32`, `i64`, `f32`, `f64`, plus vectors and references), one or more linear memories, and no notion of strings, records or who may call what. The base build of the corelib (`buildWasm("base")` in `tools/corelib.ts`) is such a module: it exports `ay_syscall(nr, a0, a1, a2) -> i32`, and a host written by hand (`corelib/host/host.ts`) must know that `ay_scratch` returns a pointer into memory and that an app is another module exporting `step`.

A component wraps core modules and adds a type layer. The Component Model repository describes where it stands: it "is being standardized" and is "developed incrementally as part of WASI Developer Preview releases" (https://github.com/WebAssembly/component-model, read 2026-11-16). It is a developer-preview design, not a finished W3C standard. What it adds:

- **Typed interfaces.** Functions take and return strings, lists, records, variants, options, results and resources. The interface is written in WIT (section 7.2) and checked by the toolchain, not by convention.
- **Shared-nothing instances.** Each core instance inside a component keeps its own linear memory; other components never see it. The README lists "shared-nothing and shared-everything linking" among the 0.2.0 features. Data crosses a boundary only as values the canonical ABI copies.
- **The canonical ABI.** A fixed rule maps each WIT type to core values: scalars lower to one core value, strings and lists to a `(pointer, length)` pair in the callee's memory (allocated through an exported `cabi_realloc`), results larger than one value through a return pointer. The code that does the mapping ("lift" and "lower") is generated by the toolchain, and the host runtime applies it at each boundary.
- **Resources.** An opaque handle type with methods (`own<T>` / `borrow<T>`), the same idea as the capability handles of `ay_abi.h` (section 7.9).
- **Async (WASI 0.3).** `async` functions and the `stream<T>` and `future<T>` types are part of the component model from 0.3.0 on, which "adds `async` functions, `stream`s and `future`s" (same README).

The cost: a component boundary is a copy plus a check, not a call. For the corelib this costs nothing visible, because every type is a scalar (section 7.4).

## 7.2 WIT and worlds

WIT is the interface definition language. An `interface` is a named set of types and functions; a `world` states what a component imports and exports, and is the unit a tool checks a component against. `corelib/wit/ay-corelib.wit` describes the corelib contract. The package has four interfaces and four worlds:

- `host`: `console-put(byte: u8)`, what the platform gives the corelib (the serial port; the `put` callback of `ay_console` in `corelib/src/core.h`).
- `scheduler`: `boot`, `spawn`, `sched-next`, `sched-report`, the platform driver's view of the exports `ay_boot`, `ay_spawn`, `ay_sched_next` and `ay_sched_report` of `corelib/src/wasm.c`.
- `syscall`: `call(number, a0, a1, a2) -> s32`, the one import of an app.
- `task`: `step() -> s32`, the one export of an app.
- worlds `corelib` (imports `host`, exports `scheduler` and `syscall`), `app` (imports `syscall`, exports `task`), `console` (a console on WASI standard output) and `driver` (a WASI command that loops over a scheduler).

<!-- listing file:corelib/wit/ay-corelib.wit -->
```text
/// The host contract of the corelib as typed interfaces. The core module that the plain wasm build exports with
/// C names (`ay_boot`, `ay_syscall`, ...) gets the same functions here, with a canonical ABI the toolchain checks.
package ay:corelib@0.1.0;

/// What the platform gives the corelib: the serial port of this machine.
interface host {
  console-put: func(byte: u8);
}

/// The platform driver's view of the corelib: boot it, create the boot task, loop over its scheduler.
interface scheduler {
  /// Run the boot self-test; 0 when every check held.
  boot: func() -> s32;
  /// Create the boot task; its id, or a negative error.
  spawn: func() -> s32;
  /// Next task to run, or -1 when none is runnable.
  sched-next: func() -> s32;
  /// Report what `step` returned for task `id` (0 done, 1 yield, 2 fault).
  sched-report: func(id: u32, code: s32);
}

/// The syscall ABI of `include/ay_abi.h`: the only way out of an app's sandbox.
interface syscall {
  call: func(number: u32, a0: u32, a1: u32, a2: u32) -> s32;
}

/// What an app exports: one slice of work per call.
interface task {
  step: func() -> s32;
}

/// The corelib itself: needs a console, offers a scheduler and the syscall ABI.
world corelib {
  import host;
  export scheduler;
  export syscall;
}

/// An app: reaches the corelib through `syscall` and nothing else.
world app {
  import syscall;
  export task;
}

/// A console backed by WASI standard output.
world console {
  import wasi:cli/stdout@0.2.12;
  export host;
}

/// A command that drives one app under the corelib's scheduler.
world driver {
  import scheduler;
  import task;
  export wasi:cli/run@0.2.12;
}
```
<!-- /listing -->

Two WASI packages are needed by `console` and `driver`. `corelib/wit/deps/io.wit` and `deps/cli.wit` are subsets of `wasi:io@0.2.12` and `wasi:cli@0.2.12`, with the signatures copied unchanged from `crates/wasi/src/p2/wit/deps/` of bytecodealliance/wasmtime v50.0.2; I trimmed them to the items `stdout` and `run` use so the repository does not vendor six large WASI packages. A host accepts such an import because an import is satisfied by any host instance that offers at least those items; Wasmtime accepted it (section 7.6).

The pipeline for one component:

1. Build a **core module** whose import and export names follow the canonical ABI naming: an import is `("<interface>@<version>", "<function>")` and an export is `"<interface>@<version>#<function>"`. wit-bindgen emits exactly these names for its guest languages; section 7.4 produces them from C with one attribute.
2. `wasm-tools component embed WIT --world W module.wasm -o module.embed.wasm` adds a custom section with the encoded world, so that the module carries its own contract. It accepts text (`.wat`) input too.
3. `wasm-tools component new module.embed.wasm -o component.wasm` checks the module against the world and wraps it: it adds the lift and lower canonical functions and the component-level types. When a name is wrong it fails with a message such as `module requires an import interface named ay:corelib/host`; this is how I found that the package version `@0.1.0` is part of the name.
4. `wasm-tools component wit component.wasm` prints the interface of any component back as WIT; `wasm-tools component targets WIT --world W component.wasm` verifies it conforms to a world.

`wasm-tools compose` still exists in v1.263.0 but prints `WARNING: wasm-tools compose has been deprecated. Please use wac instead.` In my run it also left `host` and `syscall` as unresolved imports of the composed result, so this chapter uses `wac`. `wit-bindgen` is not used here: the corelib's interface is five scalar functions, so the names are one line each and I wrote them by hand. For anything with strings, lists or records, use it.

Rust is not used here: ADR-0008 (`docs/adr/0008-sdk-languages-toolchain.md`) keeps Rust in `aphrody-dev/aphrody` and makes the SDK C, assembly, WAT and Bun, with wasm getting "the same ABI as imports/exports and a WIT world". For information only, `rustc --print target-list` (rustc 1.102.0-nightly, 2026-11-11) lists `wasm32-wasip1`, `wasm32-wasip2`, `wasm32-wasip3` and `wasm32-none-component`, so Rust can emit components directly. In this chapter the component is made from a plain core module by `wasm-tools`, whatever the source language.

## 7.4 The corelib as a component

The corelib is one C code base (`corelib/src/*.c`). `corelib/src/wasm.c` is its WebAssembly platform layer, and it builds in two shapes from the same functions. Plain, it exports `ay_boot`, `ay_syscall` and so on and imports `ay_host.console_put`, which is what the hand-written host of chapter 8 expects. With `-DAY_COMPONENT` the same functions carry the canonical ABI names of the WIT: `ay:corelib/scheduler@0.1.0#boot` and the import `("ay:corelib/host@0.1.0", "console-put")`. `wasm-tools component new` accepts only the second shape. The names are chosen by two macros and clang's `export_name` / `import_module` / `import_name` attributes, so no generator is involved:

<!-- listing file:corelib/src/wasm.c#6-24 -->
```c
#include "core.h"

#ifdef AY_COMPONENT
#define IMPORT_MODULE "ay:corelib/host@0.1.0"
#define IMPORT_NAME "console-put"
#define NAME(plain, canonical) canonical
#else
#define IMPORT_MODULE "ay_host"
#define IMPORT_NAME "console_put"
#define NAME(plain, canonical) plain
#endif
#define EXPORT(plain, canonical) [[clang::export_name(NAME(plain, canonical))]]

[[clang::import_module(IMPORT_MODULE), clang::import_name(IMPORT_NAME)]] extern void host_console_put(uint32_t byte);

static void put(void *, uint8_t byte) { host_console_put(byte); }

static const ay_console host = {put, nullptr};
static ay_core core = {.cursor = AY_MAX_TASKS - 1};
```
<!-- /listing -->

<!-- listing file:corelib/src/wasm.c#26-48 -->
```c
/// Run the boot self-test; 0 when every check held.
EXPORT("ay_boot", "ay:corelib/scheduler@0.1.0#boot") int32_t ay_boot(void) { return ay_selftest(&host) ? 0 : -1; }

/// Create the boot task; its id or a negative error.
EXPORT("ay_spawn", "ay:corelib/scheduler@0.1.0#spawn") int32_t ay_spawn(void) {
  return ay_core_spawn(&core, ay_boot_caps, 2);
}

/// Next task to run, or -1 when none is runnable.
EXPORT("ay_sched_next", "ay:corelib/scheduler@0.1.0#sched-next") int32_t ay_sched_next(void) {
  return ay_core_schedule(&core, &host);
}

/// Report what `step` returned for task `id` (0 done, 1 yield, 2 fault).
EXPORT("ay_sched_report", "ay:corelib/scheduler@0.1.0#sched-report") void ay_sched_report(uint32_t id, int32_t code) {
  ay_core_report(&core, &host, id, code);
}

/// The syscall ABI: what an app's `ay.syscall` import resolves to.
EXPORT("ay_syscall", "ay:corelib/syscall@0.1.0#call")
int32_t ay_syscall(uint32_t nr, uint32_t a0, uint32_t a1, uint32_t a2) {
  return ay_core_syscall(&core, &host, nr, a0, a1, a2);
}
```
<!-- /listing -->

The build, as `buildWasm("component")` in `tools/corelib.ts` runs it (clang 23.1.5 on this PC, 23.1.6 on `fr1`; sources are every `corelib/src/*.c` except `wasm.c`, then `wasm.c`):

```text
clang --target=wasm32 -mcpu=mvp -std=c23 -O2 -ffreestanding -fno-stack-protector -fvisibility=hidden \
  -Wall -Wextra -Werror -Icorelib/include -Icorelib/src -DAY_COMPONENT -nostdlib \
  -Wl,--no-entry -Wl,-z,stack-size=65536 -Wl,--initial-memory=131072 \
  -o target/corelib/wasm-component/corelib.wasm \
  corelib/src/{abi,apps,cap,demo,engine,ipc,libc,mem,out,sync}.c corelib/src/wasm.c
```

`-ffreestanding` and `-nostdlib` mean no C library (`corelib/src/libc.c` supplies the few functions the compiler may emit), `-mcpu=mvp` restricts the output to the WebAssembly 1.0 feature set, and the 64 KiB shadow stack and two initial pages (131072 bytes) keep the linear memory small. The plain variant adds `-Wl,--export-dynamic`; the component variant does not, because the exports come from the attributes alone. `wasm-tools print` of the resulting core module lists exactly one import and six exports:

```text
(import "ay:corelib/host@0.1.0" "console-put" (func (param i32)))
(export "memory" (memory 0))
(export "ay:corelib/scheduler@0.1.0#boot" (func 12))
(export "ay:corelib/scheduler@0.1.0#spawn" (func 13))
(export "ay:corelib/scheduler@0.1.0#sched-next" (func 14))
(export "ay:corelib/scheduler@0.1.0#sched-report" (func 15))
(export "ay:corelib/syscall@0.1.0#call" (func 16))
```

Every WIT type here is a scalar (`u8`, `u32`, `s32`), which lowers to one `i32` each, so the module needs no `cabi_realloc` and no post-return. `wasm-tools component wit corelib.wasm` prints what the toolchain extracted:

```text
package root:component;

world root {
  import ay:corelib/host@0.1.0;

  export ay:corelib/scheduler@0.1.0;
  export ay:corelib/syscall@0.1.0;
}
```

`wasm-tools component targets corelib/wit --world corelib corelib.wasm` returns success, so the component conforms to world `corelib`. The core module is 8393 bytes and the component 10215 bytes (the core module plus the canonical wrapper), built with clang 23.1.5 on this PC.

The three other pieces are written in WAT, because they are short and show the canonical ABI at the instruction level.

**The console** imports WASI standard output. A `list<u8>` argument is `(pointer, length)` in the caller's memory; the `result<_, stream-error>` return is written through a trailing pointer. The stream handle is fetched once and kept, because each `get-stdout` call returns a new owned handle.

<!-- listing file:corelib/wat/console.wat -->
```wat
;; Core module of `world console`: ay:corelib/host@0.1.0.console-put over WASI stdout.
;; Canonical ABI: a `list<u8>` argument is (pointer, length) in linear memory; the `result<_, stream-error>`
;; return value is written through a trailing pointer.
(module
  (import "wasi:cli/stdout@0.2.12" "get-stdout" (func $get_stdout (result i32)))
  (import "wasi:io/streams@0.2.12" "[method]output-stream.blocking-write-and-flush"
    (func $write (param i32 i32 i32 i32)))

  (memory (export "memory") 1)
  (global $out (mut i32) (i32.const -1))   ;; the stream handle, fetched on first use

  (func (export "ay:corelib/host@0.1.0#console-put") (param $byte i32)
    (if (i32.lt_s (global.get $out) (i32.const 0))
      (then (global.set $out (call $get_stdout))))
    (i32.store8 (i32.const 0) (local.get $byte))
    (call $write (global.get $out) (i32.const 0) (i32.const 1) (i32.const 16))))   ;; result at 16
```
<!-- /listing -->

**The driver** is the platform driver of `host.ts` as a WASI command, written against the scheduler and task interfaces. `wasi:cli/run.run` returns `result<_, _>`, which lowers to an `i32` (0 ok, 1 error). It handles exactly one app: the single task id that `spawn` returns is the id of the single `task` instance.

<!-- listing file:corelib/wat/driver.wat -->
```wat
;; Core module of `world driver`: the platform driver of the Wasm OS as a WASI command.
;; Same loop as host.ts: boot, spawn the boot task, run `step` under the corelib's scheduler.
;; One app only: the single task id spawned is the id of the single `task` instance.
(module
  (import "ay:corelib/scheduler@0.1.0" "boot" (func $boot (result i32)))
  (import "ay:corelib/scheduler@0.1.0" "spawn" (func $spawn (result i32)))
  (import "ay:corelib/scheduler@0.1.0" "sched-next" (func $sched_next (result i32)))
  (import "ay:corelib/scheduler@0.1.0" "sched-report" (func $sched_report (param i32 i32)))
  (import "ay:corelib/task@0.1.0" "step" (func $step (result i32)))

  ;; wasi:cli/run.run returns result<_, _>: 0 is ok, 1 is error.
  (func (export "wasi:cli/run@0.2.12#run") (result i32)
    (local $id i32)
    (if (call $boot) (then (return (i32.const 1))))
    (if (i32.lt_s (call $spawn) (i32.const 0)) (then (return (i32.const 1))))
    (loop $next
      (local.set $id (call $sched_next))
      (if (i32.ge_s (local.get $id) (i32.const 0))
        (then
          (call $sched_report (local.get $id) (call $step))
          (br $next))))
    (i32.const 0)))
```
<!-- /listing -->

**The app** is `corelib/wat/hello.wat`, unchanged. The script renames its import `("ay", "syscall")` to `("ay:corelib/syscall@0.1.0", "call")` and its export `step` to `ay:corelib/task@0.1.0#step` as text before assembling, and then embeds world `app`:

<!-- listing file:tools/corelib-component.ts#36-42 -->
```ts

/** The app is hello.wat with its import and export renamed to the canonical ABI names of `world app`. */
export function appWat(hello: string): string {
  return hello
    .replace('(import "ay" "syscall"', `(import "ay:corelib/syscall@${PKG}" "call"`)
    .replace('(export "step"', `(export "ay:corelib/task@${PKG}#step"`);
}
```

## 7.5 Composition

Components are wired by name: the `host` import of the corelib is satisfied by the console's `host` export, the app's `syscall` import by the corelib's export, and the driver's `scheduler` and `task` imports by the corelib and the app. `wac` states this as a small program:

<!-- listing file:tools/corelib-component.ts#43-60 -->
```ts

/** The composition script: who plugs into whom. */
export function wacScript(): string {
  const i = (name: string) => `"ay:corelib/${name}@${PKG}"`;
  return [
    "package ay:os;",
    "",
    "let console = new ay:console { ... };",
    `let corelib = new ay:corelib { ${i("host")}: console[${i("host")}] };`,
    `let app = new ay:app { ${i("syscall")}: corelib[${i("syscall")}] };`,
    "let driver = new ay:driver {",
    `  ${i("scheduler")}: corelib[${i("scheduler")}],`,
    `  ${i("task")}: app[${i("task")}],`,
    "};",
    "",
    'export driver["wasi:cli/run@0.2.12"];',
    "",
  ].join("\n");
```
<!-- /listing -->

The text it writes, `ay-os.wac`:

```text
package ay:os;

let console = new ay:console { ... };
let corelib = new ay:corelib { "ay:corelib/host@0.1.0": console["ay:corelib/host@0.1.0"] };
let app = new ay:app { "ay:corelib/syscall@0.1.0": corelib["ay:corelib/syscall@0.1.0"] };
let driver = new ay:driver {
  "ay:corelib/scheduler@0.1.0": corelib["ay:corelib/scheduler@0.1.0"],
  "ay:corelib/task@0.1.0": app["ay:corelib/task@0.1.0"],
};

export driver["wasi:cli/run@0.2.12"];
```

`wac compose ay-os.wac --dep ay:console=console.wasm --dep ay:corelib=corelib.wasm --dep ay:app=app.wasm --dep ay:driver=driver.wasm -o ay-os.wasm` produces one component (16430 bytes on this PC with clang 23.1.5, 16413 bytes on `fr1` with clang 23.1.6). Its own interface is only what is left unsatisfied, WASI standard output, and what it offers, the `wasi:cli/run` command:

```text
world root {
  import wasi:io/error@0.2.12;
  import wasi:io/streams@0.2.12;
  import wasi:cli/stdout@0.2.12;

  export wasi:cli/run@0.2.12;
}
```

Composition is also where the isolation shows. The app component imports `syscall` and nothing else; the composed graph gives it no console, no WASI and no memory of the corelib. The corelib's `host` import is reachable only from the corelib. This is the structure the capability table of chapter 8 enforces inside one module, now enforced between components by the type system and the linker.

### Reproducing it

`tools/corelib-component.ts` does all of it. Locally it builds, componentizes, composes (downloading the latest `wac` release into `target/tools` when it is not on `PATH`) and runs with the `wasmtime` on `PATH` or the latest release; with `--remote` it ships the sources to the build host of `ay.toml`, builds and runs there, and copies the transcript back.

```text
$ bun tools/corelib-component.ts --no-run
component: $WORKSPACE_ROOT/ay/target/corelib-component/ay-os.wasm (16430 bytes)

$ bun tools/corelib-component.ts --remote
component: $WORK/asm-guide/corelib-component/target/corelib-component/ay-os.wasm (16413 bytes)
wasmtime: wasmtime 50.0.2 (f9a93b049 2026-11-16)
wasmtime: boot transcript identical (13 lines), log $WORK/asm-guide/corelib-component/logs/wasmtime-boot.log
wasmtime: fr1:$WORK/asm-guide/corelib-component/logs/wasmtime-boot.log copied to $WORKSPACE_ROOT/ay/target/corelib-component.log

The build host used its own `wasm-tools` 1.261.0 and clang 23.1.6; this PC used `wasm-tools` 1.263.0 and clang 23.1.5. The sizes differ by 17 bytes (16413 against 16430 for the composed component; the corelib component is 10198 bytes on `fr1` and 10215 on this PC), so I did not assume the builds are byte-identical, only that both transcripts equal the golden one. The only build prerequisites are clang with the wasm32 backend and `wasm-ld`, `wasm-tools`, `wac` and Wasmtime; there is no cargo step.

 - out/corelib.d.ts                          0.33 KiB
 - out/corelib.js                             139 KiB
 - out/interfaces/ay-corelib-host.d.ts       0.09 KiB

With 0.3 the same shape would be a `stream<u8>` the corelib writes to, so a console becomes an asynchronous byte sink; the corelib's cooperative `step()` loop and the component model's async both avoid threads, but they are different mechanisms and I have not connected them.

## 7.9 WASI handles and the capability model of the corelib

WASI 0.2 is already capability-based in the object sense: a component has no ambient authority; it can only use the resources it was handed. In the chapter's graph, the console component can write because the linker gave it `wasi:cli/stdout`, and `get-stdout` returns an `own<output-stream>` handle, an index in a per-instance table. The corelib's `ay_abi.h` has the same shape:

| | WASI / component model | `include/ay_abi.h` |
|---|---|---|
| Handle | `own<T>` / `borrow<T>`, index into the instance's resource table | capability handle, index into the task's table of 8 entries |
| Authority | exists only if a resource was passed or imported | exists only if the task holds a handle (`AY_EPERM` or `AY_EBADCAP` otherwise) |
| Narrowing | a host or a virtualizing component can wrap an interface with fewer functions | `CAP_DERIVE(cap, mask)` creates a handle with `rights & mask`; needs the `DERIVE` right |
| Granularity | per interface and per resource | three rights (`SEND`, `RECV`, `DERIVE`) on two object kinds |
| Enforced by | the type system at link time and the host at run time | `ay_core_syscall` at run time |

Differences to keep in mind: a component's capabilities are decided at composition time by what is wired to its imports, while the corelib's are runtime state of a task, which can narrow them but never widen them; and the corelib has no equivalent of the type-checked interface, so the app/corelib boundary relies on the `ay.syscall` signature alone. Making `syscall` a WIT interface (this chapter) moves that signature under the toolchain's checking without changing the rights logic inside the corelib. The corelib's single `call` function is also the coarse choice; a finer WIT design would give each object kind its own interface (a `console` resource with `log`, an `endpoint` resource with `send` and `recv`) so that holding the resource is holding the capability, which is what WASI does. This is a design option, not implemented here.
