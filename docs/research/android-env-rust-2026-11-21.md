# Android app environment in pure Rust: OpenBook, Waydroid, WSABuilds (research, 2026-11-21)

Deep-research workflow wf_c7cbef26-f45: 105 agents, 3-vote adversarial verification per claim.

## Summary

Only part of the research question is answered by verified claims. OpenBook is a bare-metal Android 17 desktop OS (pre-alpha, one laptop), not a container, so there is nothing in it to port to Windows or WASM. WSABuilds only repackages Microsoft's discontinued WSA (LTS, v2407 base) and reports NVIDIA GPU problems. The best verified Rust building blocks are youki's libcontainer/libcgroups crates (Linux-only), smithay (Wayland compositor toolkit, Linux-centric), and rutabaga_gfx (virtio-gpu with gfxstream/Venus capsets, Linux host only documented). The Windows 11 path rests on Microsoft's GPU-PV/dxgkrnl, which gives Linux guests GPU access through /dev/dxg, so the realistic design is a Rust Linux guest (Android container or VM) on Hyper-V/WSL2 with GPU-PV, and no verified source covers a native-Windows or in-browser Android runtime. Waydroid's own architecture, a pure-Rust Waydroid equivalent, and the WASM/WebGPU path were not established by the surviving claims, so the architecture below is inference, not verified fact, and a Windows 11 Insider build with an NVIDIA driver was not specifically verified.

## Verified findings

- **high** (3-0 (claims 0 and 1)): OpenBook is a bare-metal Android 17 (AOSP 17) desktop OS for x86_64 laptops: GKI 6.18 kernel rebuilt from source, open AMD and NVIDIA (615.78.08 open kernel driver with GSP firmware) vendor modules, raw GPT image with systemd-boot and A/B update slots. It is not a Waydroid or WSA-style container. Status is pre-alpha with release 0.1.0-preview.2 (2026-10-31, userdebug, test keys), targeting only the ASUS ROG Zephyrus G14; Intel laptops are planned. Its license text says Apache-2.0 but the badge says pending. There is nothing in it to port to Windows or WASM, so for fw it is a design reference (Android desktop shell, freeform windows, A/B updates), not a runtime to wrap.
  - https://github.com/Mhsbrian/OpenBook https://openbook.page/
- **high** (3-0 (claim 2)): OpenBook's NVIDIA path is incomplete: the open NVIDIA driver binds and the GPU powers off when idle, but apps do not yet render on the NVIDIA GPU. Deep sleep (S0i3) is not reached, Bluetooth audio is not working, and speakers and webcam are untested on the site.
  - https://openbook.page/ https://github.com/Mhsbrian/OpenBook
- **high** (3-0 (claims 3 and 4)): WSABuilds repackages Microsoft's discontinued WSA as prebuilt Windows 10/11 images, with optional MindTheGapps and Magisk/KernelSU root. It is not an independent Android runtime. The repo is not archived and is kept in LTS mode: the latest release is LTS 8 Hotfix (v2407.40000.4.0, published 2026-09-04). It rests on a frozen WSA v2407 base and the Windows virtualization features. Microsoft ended WSA and Amazon Appstore support on 5 March 2025.
  - https://github.com/MustardChef/WSABuilds
- **medium** (3-0 (claim 5)): WSABuilds documents stability limits relevant to the NVIDIA requirement. GApps builds crash on all Windows 11 builds after June 2025 (tracking issue #700 still open). Nvidia GPUs are known to cause problems. Intel HD 530 and older may fail or glitch, with no known fix. Suggested workarounds are another iGPU/dGPU/eGPU or Microsoft Basic Renderer.
  - https://github.com/MustardChef/WSABuilds
- **high** (3-0 (claim 6)): Smithay supplies building blocks for Wayland compositors in Rust and is explicitly not a full compositor or a framework, so fw would write the compositor logic itself. It provides core Wayland protocols, official extensions and some wlroots/KDE extensions, and ships an anvil reference compositor. Production compositors built on it include Cosmic, Niri and MagmaWM.
  - https://github.com/smithay/smithay
- **medium** (3-0 (claim 7)): Smithay is Linux-centric. Its system dependencies are libwayland, libxkbcommon, libudev, libinput, libgbm, libseat, xwayland, libEGL, libpixman and libdisplay-info, and its default features are DRM/GBM/libinput/udev/libseat/xwayland/X11 backends. CI runs only on ubuntu-24.04. The README does not claim Windows or WASM support. Some dependencies are feature-gated, but even the protocol layer relies on Unix fds and sockets, so on Windows or WASM Smithay is more likely unusable than partially usable and the compositor must run inside a Linux guest.
  - https://github.com/smithay/smithay
- **medium** (3-0 (claim 8); runc-equivalence claim refuted 0-3): youki is split into reusable crates published on crates.io: libcontainer 0.7.0, libcgroups 0.7.0, liboci-cli 0.7.0 (all published 2026-07-25) and oci-spec 0.10.0 (2026-05-27, from a separate repo). Container and cgroup logic can therefore be embedded as Rust libraries. libcontainer is Linux-only and has system dependencies (libseccomp, libbpf). It is the best verified Rust building block for the LXC-replacement layer, inside a Linux guest only. A claim that youki is a runc-comparable pure-Rust runtime usable as the container layer of a Waydroid equivalent was refuted 0-3, so treat that framing as unproven. Binder/ashmem and Android-specific container needs are not covered by any verified claim.
  - https://docs.rs/youki https://github.com/youki-dev/youki
- **medium** (2-1 (claims 9 and 10)): rutabaga_gfx 0.1.85 (published 2026-08-06, BSD-3-Clause, repo github.com/magma-gpu/rutabaga_gfx) is the Rust crate for 2D/3D virtio-gpu hypercalls plus swapchain allocation and mapping. It exposes nine capsets: CROSS_DOMAIN, DRM, GFXSTREAM_COMPOSER, GFXSTREAM_GLES, GFXSTREAM_VULKAN, MAGMA, VENUS, VIRGL and VIRGL2. One Rust API can therefore front both Android graphics (gfxstream) and Linux Vulkan (Venus). The working backends need native components (the gfxstream and virglrenderer libraries), and the Rust crate is only the wrapper layer.
  - https://docs.rs/rutabaga_gfx/latest/rutabaga_gfx/ https://crates.io/crates/rutabaga_gfx
- **high** (3-0 (claim 11)): rutabaga_gfx host support is documented for Linux only. docs.rs builds only x86_64-unknown-linux-gnu and RutabagaPath says only Linux hosts are considered at the moment. Windows and wasm support are undocumented and must be verified separately. The 0.1.85 source contains partial Windows plumbing (a cfg(windows) branch in vulkano_gralloc, gralloc tests ignored on windows and macos), and a QEMU patch description says gfxstream can use ANGLE for GLES on Windows and macOS hosts. For the Windows 11 path, rutabaga cannot be assumed to run on the host, and for browser WASM it should be treated as unsupported.
  - https://docs.rs/rutabaga_gfx/latest/rutabaga_gfx/
- **high** (3-0 (claims 12 and 13)): QEMU's virtio-gpu documents a rutabaga backend that forwards GLES and Vulkan to the host via gfxstream, with experimental Android-specific capsets (x-gfxstream-gles, x-gfxstream-composer). Vulkan paravirtualization via Venus is supported since virglrenderer v1.0.0 and needs host blob support. The Vulkan pass-through requirements table is host Linux 6.13+, libvirglrenderer 1.0.0+, guest Linux 5.16+ and Mesa 24.2.0+. This is a documented but experimental path for Android guest graphics, not a production-ready one. The gfxstream renderer is Google's C++ library, so only the rutabaga wrapper is Rust.
  - https://www.qemu.org/docs/master/system/devices/virtio/virtio-gpu.html
- **medium** (3-0 (claim 14); rutabaga_gfx_ffi claim refuted 0-3): Backend choice. gfxstream is the cross-platform option, shipping in the Android Emulator and Google Play Games on PC, while Venus targets open-source Linux platforms, initially Chromebook gaming, and no source shows Venus on a Windows host. For Android on Windows 11 the design intent therefore favours gfxstream. The source is a Mar 2023 qemu-devel message by a Google gfxstream engineer and states design intent, not a current benchmark. The Windows/macOS support line in it sits under the gfxstream GLES heading, a minor stretch. The related claim that QEMU would consume gfxstream via the rutabaga_gfx_ffi.h C proxy, with Rust packaging the main obstacle, was refuted 0-3.
  - https://lists.gnu.org/archive/html/qemu-devel/2023-03/msg05068.html
- **high** (3-0 (claims 15, 16 and 18)): Windows 11 GPU path: Microsoft's WSL2 GPU stack uses dxgkrnl, a clean-room Linux kernel driver that exposes /dev/dxg with IOCTLs mirroring the WDDM D3DKMT layer, open-sourced in the WSL2 kernel branch (an lkml v4 upstreaming series dated March 2026 shows it is still being upstreamed). GPU-PV has existed since Windows 10 1803 (WDDM 2.4) for Windows guests, and WDDM 2.9 extended it to Linux guests. Microsoft lists Linux in a VM with GPU acceleration as a client scenario. Linux guest support needs the WDDM 2.9 era, not 1803. This is the verified basis for an NVIDIA path on Windows 11: the NVIDIA Windows driver exposes the GPU to a Linux guest through GPU-PV, and the guest sees /dev/dxg. The 2020 post says all host GPUs are projected without resource partitioning, but only if all run WDDM 2.9 drivers, and community reports show multi-GPU setups seeing only one GPU, so do not rely on all GPUs being exposed.
  - https://devblogs.microsoft.com/directx/directx-heart-linux/ https://learn.microsoft.com/windows-hardware/drivers/display/gpu-paravirtualization
- **medium** (2-1 (claim 17)): Microsoft's guest user mode is libd3d12.so (built from the same source as d3d12.dll for a Linux target) plus libdxcore.so (a simplified DXGI), both closed-source binaries that ship with Windows. This is Microsoft's own D3D12 on Linux, not Mesa d3d12 or dozen. Mesa's d3d12 Gallium and dzn drivers sit on top of it. At publication WSL had no presentation integration, and Present() was the only D3D12 exception, so output needs a separate path. WSLg (April 2021) later supplied that path via Wayland/RDP, which is consistent but separate evidence.
  - https://devblogs.microsoft.com/directx/directx-heart-linux/
- **low** (1-2 and 0-3 (refuted)): Waydroid is not covered by any surviving claim. The container-based, not-a-VM claim was refuted 1-2 and the six-namespaces/direct-hardware claim 0-3 (the vote record does not say why). Waydroid's architecture (LXC, binder/ashmem, gbinder, Wayland, image builds), its license and its 2026 status therefore remain unverified. Any statement that a Rust port must replicate Linux namespace primitives is unconfirmed by this research.
  - https://github.com/waydroid/waydroid https://github.com/orgs/waydroid/repositories
- **low** (n/a (synthesis)): Proposed pure-Rust architecture (design inference from the verified blocks, not a sourced fact). One fw feature built on a Linux guest: the host runtime is a Rust VMM on Hyper-V/WHP (Windows 11, GPU-PV with the NVIDIA driver) or KVM (Linux). The guest is Android or a Linux userland, with containers via youki's libcontainer/libcgroups and a Smithay-based Wayland compositor for window output. Graphics are virtio-gpu through rutabaga_gfx, with gfxstream for Android GLES/Vulkan and Venus for Linux Vulkan. Windows adds a /dev/dxg GPU-PV path. OpenBook-style A/B images and rollback are the update model. Browser WASM is a separate, limited target: no verified source supports running Android or a Linux container inside WASM, and rutabaga and Smithay are not documented for wasm. The browser would at most be a thin client that streams the guest or a Wayland-protocol display, with wgpu's WebGPU backend rendering only the client UI. Treat it as a feasibility gap, not a delivery.
  - https://docs.rs/youki https://github.com/smithay/smithay https://docs.rs/rutabaga_gfx/latest/rutabaga_gfx/ https://devblogs.microsoft.com/directx/directx-heart-linux/

## caveats

Time sensitivity: the OpenBook and WSABuilds statuses date from late 2026-10 and 2026-09. The Microsoft GPU-PV/dxgkrnl sources date from 2020 (the Learn page is 2025). The gfxstream/Venus design-intent source is from Mar 2023. Source quality: the OpenBook, WSABuilds and Smithay facts come from each project's own documentation, with no independent coverage. The rutabaga votes were 2-1 and the libd3d12 vote 2-1. Refuted claims (Waydroid's container architecture and namespaces, youki as a runc-equivalent runtime for a Waydroid port, the OpenBook 120 fps and full working-features list, and the rutabaga_gfx_ffi packaging claim) were not carried into the findings. Coverage gaps: no verified claim covers Waydroid internals, binder/ashmem or gbinder, input and networking paths, existing Rust binder crates, crosvm itself, Hyper-V/WHP VMM options in Rust, wgpu's wasm backend and WebGPU limits, Windows 11 Insider specifics, or NVIDIA driver specifics for GPU-PV beyond the dxgkrnl mechanism. The architecture in the last finding is a synthesis, and the claim that this can be delivered as one production-ready feature in a single session has no support in any source.
